# QA Agents — Pipeline Rules & Safety

## Pipeline Overview

This repo implements a sequential QA pipeline. Agents run in order and each stage gates the next.

```
0-framework-analyzer → 1-test-case-generator → 2-test-case-reviewer → 3-manual-tester → 4-automation-engineer
```

## Preflight Checks

Before any agent runs, verify:

- [ ] `.env` exists and `APP_URL` is set
- [ ] `context/project-overview.md` exists and is filled in
- [ ] `context/roles.md` exists
- [ ] `context/test-standards.md` exists
- [ ] The target app is reachable (`APP_URL` returns 200)
- [ ] For automation stage: `context/automation-guide.md` exists (generated by Agent 0)

If any check fails, stop and tell the user what is missing before proceeding.

## Agent Rules

### All agents must:
- Read `context/INDEX.md` before starting work
- Follow naming conventions in `context/test-standards.md`
- Use the templates in `templates/` for all output files
- Write output to the correct `data/outputs/` subfolder
- Never overwrite an existing output file — append a timestamp suffix instead

### Agent 0 — Framework Analyzer
- Runs once per project
- Reads the codebase or app structure to understand the automation framework
- Writes findings to `context/automation-guide.md`
- Does not write to `data/outputs/`

### Agent 1 — Test Case Generator
- Input: one `.md` file from `data/inputs/`
- Output: one file in `data/outputs/1-test-cases/` named `<input-name>-test-cases.md`
- Generates both positive and negative test cases
- Tags each case with: module, priority (P0/P1/P2/P3), type (functional/UI/API/security)

### Agent 2 — Test Case Reviewer
- Input: one file from `data/outputs/1-test-cases/`
- Output: one file in `data/outputs/2-reviews/` named `<input-name>-reviewed.md`
- Checks: coverage gaps, duplicate cases, missing edge cases, incorrect priorities
- Annotates each case with APPROVED / NEEDS-REVISION / REJECTED + reason
- Summary section with overall quality score (0–100)

### Agent 3 — Manual Tester
- Input: reviewed test case file from `data/outputs/2-reviews/`
- Only executes cases marked APPROVED
- Uses Playwright MCP to interact with the browser
- Records PASS / FAIL / BLOCKED for each case with evidence (screenshot path or error message)
- Output: execution report in `data/outputs/3-execution-reports/`

### Agent 4 — Automation Engineer
- Input: execution report from `data/outputs/3-execution-reports/`
- Reads `context/automation-guide.md` for framework conventions
- Generates Playwright TypeScript tests for all PASS cases
- Output: `.spec.ts` files in `data/outputs/4-automation/`
- Each test file must include a brief comment explaining what it covers

## Safety Rules

- **Never use production credentials** — only use credentials from `.env` pointing at staging/test environments
- **Never delete or modify files in `data/inputs/`** — they are user-owned source of truth
- **Never commit `.env`** — it is in `.gitignore`
- **Do not execute destructive actions** (delete accounts, wipe data, submit financial transactions) even if a test case asks for it — flag it and ask the user
- **Respect rate limits** — add a minimum 500ms delay between Playwright actions in generated scripts
- **Screenshot on failure** — always capture a screenshot when a test step fails

## Output File Naming

| Stage | Pattern |
|-------|---------|
| Test cases | `<feature>-test-cases-YYYYMMDD.md` |
| Reviews | `<feature>-reviewed-YYYYMMDD.md` |
| Execution reports | `<feature>-execution-YYYYMMDD.md` |
| Automation | `<feature>.spec.ts` |

## Context Files (never auto-overwrite)

- `context/project-overview.md`
- `context/roles.md`
- `context/test-standards.md`
- `context/modules/*.md`

These are human-maintained. Agents may read them but must not overwrite them. Agent 0 may create `context/automation-guide.md` if it does not already exist.
